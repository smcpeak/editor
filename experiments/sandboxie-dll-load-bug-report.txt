Title: Sandboxie may prevent a program from loading a DLL after trying to access a long file name
Link: https://github.com/sandboxie-plus/Sandboxie/issues/5754


In short
--------

If a program running under Sandboxie first tries to access a very long (~3k characters) file name (for example, with `NtOpenFile`), then attempts to open a DLL with `LoadLibraryW`, the latter may fail with error code 998 (ERROR_NOACCESS).

Outside Sandboxie, the first call fails (its final component is too long), but subsequent DLL loading still succeeds.


Original failure scenario
-------------------------

I run Claude Code under Sandboxie.  It sometimes runs `bash` with very long command lines (that typically contain python scripts to run).  The `bash` command typically contains space characters enclosed in double-quotes, whose presence causes the `bash` startup code to attempt file name globbing.  That involves checking if the name exists on the file system (hence the file access check).  Afterward, `bash` loads `iphlpapi.dll` on demand (I'm not sure which function triggers that, but it happens every time), and that load fails, causing `bash` to fail with an error like:

```
  0 [main] bash 421 C:\opt\Git4Win-2.56.1\usr\bin\bash.exe: *** fatal error - unable to load iphlpapi.dll, Win32 error 998
```

This affects both Cygwin `bash` and MSYS2 `bash` (which Git4Win uses), as they share a common heritage.

`bash` tries the DLL load 10 times before printing that message, so it is not caused by a momentary glitch.


Working directory interaction
-----------------------------

Exactly how or whether this manifests depends on the Sandboxie file access rules.  In the original failure scenario, I observed the failure only when the current working directory was inside a directory marked as "Open for All".

The reproducer below caused the DLL load to fail with the working directory both inside and outside the "Open for All" area.  While inside "Open for All", `NtOpenFile` returned STATUS_OBJECT_NAME_INVALID (0xC0000033), as it should.  Outside of it, `NtOpenFile` returned STATUS_ACCESS_VIOLATION (0xC0000005), which might indicate a separate, more severe issue.


"Name buffer is approaching overflow"
-------------------------------------

While developing this reproducer, at one point the program caused a bunch of errors to appear in the Sandboxie UI all at once:

```
  child.exe: SBIE2310 Name buffer is approaching overflow (13)
  child.exe: SBIE2310 Name buffer is approaching overflow (14)
  child.exe: SBIE2310 Name buffer is approaching overflow (15)
  child.exe: SBIE2310 Name buffer is approaching overflow (-1)
  child.exe: SBIE2310 Name buffer is approaching overflow (-2)
  [...]
  child.exe: SBIE2310 Name buffer is approaching overflow (-16)
```

The `child.exe` (compiled from an earlier version of the reproducer code below) process then became stuck, not making any progress and not using any CPU.  The current directory was outside the "Open for All" directory, and was sweeping lengths from 1000 to 4500.  I killed it after a while, and don't know which length it was on.

Varying the `len` parameter of the reproducer may cause this to happen again.  It may or may not share a root cause with the DLL load failure.


Effect of varying length
------------------------

Sweeping the `len` over the range 1000 to 4500, the DLL load will usually fail for lengths that are within a certain window, 2200-3900 in my testing, and usually succeed outside it.

Most values will either deterministically succeed or deterministically fail, but I've seen values cause both to happen unpredictably.


Sandbox configuration
---------------------

My normal working sandbox has a default configuration, except one "Open for All", "All Programs" rule for "C:\cygwin\home\scott\wrk\editor\*".

However, the problem reproduces with DefaultBox, whose configuration I have not changed after installation.


Reproducer
----------

Save the attachment as `long-name-load.c`, then with MinGW `gcc`:

```
  $ gcc -Wall -o long-name-load.exe long-name-load.c
```

Then inside Sandboxie, here inside an "Open for All" directory:

```
  $ ./long-name-load 3000 ntopen
  long-name-load: len 3000, method ntopen
  cwd: C:\cygwin\home\scott\wrk\editor\experiments
  NtOpenFile: status 0xc0000033
  LoadLibraryW("C:\WINDOWS\system32\iphlpapi.dll"): failed, error 998
  (exit code 1)
```

The final `LoadLibraryW` error is the bug.  It should instead say "ok".

In contrast, outside Sandboxie, it looks like:

```
  $ ./long-name-load 3000 ntopen
  long-name-load: len 3000, method ntopen
  cwd: C:\cygwin\home\scott\wrk\editor\experiments
  NtOpenFile: status 0xc0000033
  LoadLibraryW("C:\WINDOWS\system32\iphlpapi.dll"): ok
```

Note the final "ok".

If we instead skip the file access call with:

```
  $ ./long-name-load 3000 ntopen
```

then the DLL load succeeds both inside and outside Sandboxie.
