Title: Sandboxie prevents a program from loading a DLL after trying to access a long file name


In short
--------

If a program running under Sandboxie first tries to access a very long
(~3kB) file name (for example, with `NtOpenFile`), then attempts to open
a DLL with `LoadLibraryW`, the latter will fail.

Outside Sandboxie, the first call (normally) fails, but subsequent DLL
loading still succeeds.


Versions
--------

Sandboxie v1.18.8
Windows 11


Original failure scenario
-------------------------

I run Claude Code under Sandboxie.  It sometimes runs `bash` with very
long command lines (that typically contain python scripts to run).  The
`bash` command typically contains (escaped) shell metacharacters whose
mere presence causes `bash` to attempt file name globbing.  That
involves checking if the name exists on the file system (hence the file
access check).  Afterward, bash loads `iphlpapi.dll` on demand (I'm not
sure which function triggers that, but it happens every time), and that
load fails, causing `bash` to fail with an error like:

  0 [main] bash 421 C:\opt\Git4Win-2.56.1\usr\bin\bash.exe: *** fatal error - unable to load iphlpapi.dll, Win32 error 998


Working directory interaction
-----------------------------

Exactly how or whether this manifests depends on the Sandboxie file
access rules.  In the original failure scenario, I observed the failure
only when the current working directory was inside a directory marked as
"Open for All".

The reproducer below will cause the DLL load to fail regardless of the
working directory, but the `NtOpenFile` error code differs depending on
the working directory's access disposition.


"Name buffer is approaching overflow"
-------------------------------------

While developing this reproducer, at one point the program caused a
bunch of errors to appear in the Sandboxie UI all at once:

  child.exe: SBIE2310 Name buffer is approaching overflow (13)
  child.exe: SBIE2310 Name buffer is approaching overflow (14)
  child.exe: SBIE2310 Name buffer is approaching overflow (15)
  child.exe: SBIE2310 Name buffer is approaching overflow (-1)
  child.exe: SBIE2310 Name buffer is approaching overflow (-2)
  [...]
  child.exe: SBIE2310 Name buffer is approaching overflow (-16)

The `child.exe` process then became stuck, not making any progress and
not using any CPU.  I killed it after a while.

Varying the `len` parameter of the reproducer will may cause this to
happen again.  It may or may not share a root cause with the DLL load
failure.


Effect of varying length
------------------------

Sweeping the `len` over the range 1000 to 5000, the DLL load will
usually fail for lengths that are within a certain window, 2200-3900 in
my testing, and usually succeed outside it.

Most values will either deterministically succeed or deterministically
fail, but I've seen values cause both to happen unpredictably.

Reproducer
----------

Save the code below as long-name-load.c, then with MinGW gcc:

  $ gcc -Wall -o long-name-load.exe long-name-load.c

Then inside Sandboxie, inside an "Open for All" directory:

  $ ./long-name-load 3000 ntopen
  long-name-load: len 3000, method ntopen
  cwd: C:\cygwin\home\scott\wrk\editor\experiments
  NtOpenFile: status 0xc0000033
  LoadLibraryW("C:\WINDOWS\system32\iphlpapi.dll"): failed, error 998
  Exit 1

The final `LoadLibraryW` error is the bug.

In contrast, outside Sandboxie, it looks like:

  $ ./long-name-load 3000 ntopen
  long-name-load: len 3000, method ntopen
  cwd: C:\cygwin\home\scott\wrk\editor\experiments
  NtOpenFile: status 0xc0000033
  LoadLibraryW("C:\WINDOWS\system32\iphlpapi.dll"): ok

Note the final "ok".


// long-name-load.c
// Open a very long file name, then load a DLL; fails under Sandboxie.

// Build (MinGW):
//
//   gcc -Wall -o long-name-load.exe long-name-load.c
//
// Usage:
//
//   long-name-load.exe <len> <method>
//
// It does one file operation on the NT path
// "\??\<cwd>\true #xxx...x", whose last component is <len> characters,
// and then calls LoadLibraryW on iphlpapi.dll (or the DLL named by the
// environment variable LNL_DLL).  The file need not exist.
//
// <method> is the file operation:
//
//   none        no file operation
//   ntopen      NtOpenFile
//   ntqa        NtQueryAttributesFile
//   createfile  CreateFileW with a \\?\ path
//
// Under Sandboxie, with <len> around 2200-3900, LoadLibraryW then
// fails with error 998 (ERROR_NOACCESS), and keeps failing on retry.
// That is the failure bash hits: when a native program starts a Cygwin
// program, Cygwin passes each double-quoted argument word to glob(),
// which stats it as a file name in the current directory.  Bash then
// loads iphlpapi.dll and fails.
//
// Exit codes: 0 if the DLL loaded, 1 if not, 2 for usage errors.

#include <windows.h>                   // Win32 API
#include <winternl.h>                  // UNICODE_STRING, OBJECT_ATTRIBUTES

#include <stdio.h>                     // printf, fprintf
#include <stdlib.h>                    // atoi
#include <string.h>                    // strcmp
#include <wchar.h>                     // swprintf, wcslen, _wgetenv


typedef NTSTATUS (NTAPI *NtOpenFile_t)(PHANDLE, ACCESS_MASK,
  POBJECT_ATTRIBUTES, PIO_STATUS_BLOCK, ULONG, ULONG);
typedef NTSTATUS (NTAPI *NtQueryAttributesFile_t)(POBJECT_ATTRIBUTES,
  PVOID);


int main(int argc, char **argv)
{
  if (argc != 3) {
    fprintf(stderr, "usage: %s <len> <method>\n", argv[0]);
    return 2;
  }
  // Unbuffered, so the output so far is visible if the program hangs.
  setvbuf(stdout, NULL, _IONBF, 0);

  int len = atoi(argv[1]);
  char const *method = argv[2];
  printf("long-name-load: len %d, method %s\n", len, method);

  // Build "\??\<cwd>\true #xxx...x".
  static WCHAR path[40000];
  WCHAR cwd[1000];
  if (!GetCurrentDirectoryW(1000, cwd)) {
    fprintf(stderr, "GetCurrentDirectoryW failed\n");
    return 2;
  }
  printf("cwd: %ls\n", cwd);
  int n = swprintf(path, 40000, L"\\??\\%ls\\true #", cwd);
  int nameStart = 4 + (int)wcslen(cwd) + 1;
  if (len < n - nameStart || nameStart + len > 32000) {
    fprintf(stderr, "invalid len: %d\n", len);
    return 2;
  }
  while (n - nameStart < len) {
    path[n++] = L'x';
  }
  path[n] = 0;

  UNICODE_STRING us;
  us.Buffer = path;
  us.Length = (USHORT)(n * sizeof(WCHAR));
  us.MaximumLength = us.Length + sizeof(WCHAR);
  OBJECT_ATTRIBUTES oa;
  InitializeObjectAttributes(&oa, &us, OBJ_CASE_INSENSITIVE, NULL,
                             NULL);

  HMODULE ntdll = GetModuleHandleW(L"ntdll.dll");

  if (!strcmp(method, "none")) {
    // Nothing.
  }
  else if (!strcmp(method, "ntopen")) {
    NtOpenFile_t f = (NtOpenFile_t)GetProcAddress(ntdll, "NtOpenFile");
    HANDLE h;
    IO_STATUS_BLOCK io;
    NTSTATUS status = f(&h, FILE_READ_ATTRIBUTES | SYNCHRONIZE, &oa,
      &io, FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE,
      FILE_OPEN_FOR_BACKUP_INTENT | FILE_OPEN_REPARSE_POINT);
    printf("NtOpenFile: status 0x%lx\n", (unsigned long)status);
  }
  else if (!strcmp(method, "ntqa")) {
    NtQueryAttributesFile_t f = (NtQueryAttributesFile_t)
      GetProcAddress(ntdll, "NtQueryAttributesFile");
    BYTE info[64];
    NTSTATUS status = f(&oa, info);
    printf("NtQueryAttributesFile: status 0x%lx\n",
      (unsigned long)status);
  }
  else if (!strcmp(method, "createfile")) {
    path[1] = L'\\';                   // "\??\" -> "\\?\"
    HANDLE h = CreateFileW(path, FILE_READ_ATTRIBUTES,
      FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE, NULL,
      OPEN_EXISTING, FILE_FLAG_BACKUP_SEMANTICS, NULL);
    if (h == INVALID_HANDLE_VALUE) {
      printf("CreateFileW: failed, error %lu\n",
        (unsigned long)GetLastError());
    }
    else {
      printf("CreateFileW: ok\n");
    }
  }
  else {
    fprintf(stderr, "unknown method: %s\n", method);
    return 2;
  }

  WCHAR const *dll = _wgetenv(L"LNL_DLL");
  if (!dll) {
    dll = L"C:\\WINDOWS\\system32\\iphlpapi.dll";
  }
  HMODULE h = LoadLibraryW(dll);
  if (!h) {
    printf("LoadLibraryW(\"%ls\"): failed, error %lu\n", dll,
      (unsigned long)GetLastError());
    return 1;
  }
  printf("LoadLibraryW(\"%ls\"): ok\n", dll);
  return 0;
}
