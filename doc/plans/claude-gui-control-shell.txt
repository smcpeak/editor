claude-gui-control-shell.txt
Plan for an interactive GUI control shell built on event replay
2026-11-22

Written by Claude Code, with small adjustments by smcpeak.


Motivation
==========

The goal is to let an agent (Claude Code) or a person drive a running
editor interactively: inspect the UI state (based on the Qt object
hierarchy), inject inputs such as keystrokes and clicks, and see the
results.  The immediate use is trying out a new dialog during
development without writing a complete .ev script blind first.

The event replay system (event-replay.{h,cc}, doc/event-replay.txt)
already has most of the pieces:

  * A command language: GDVN tagged tuples such as
    KeyPress("window1.editorFrame.m_editorWidget" "Key_X" "x"),
    dispatched by EventReplay::replayCall.
  * Addressing of widgets by QObject name path (getObjectFromPath).
  * Input synthesis: KeyPress, FocusKeySequence, Shortcut,
    TriggerAction, ClickButton, mouse events, ResizeEvent, and so on.
  * State checks: CheckLabel, CheckLineEditText, CheckFocusWidget,
    CheckQuery (via EventReplayQueryable), CheckImage, and so on.
  * Synchronization: after each command, the next is not run until the
    application reaches quiescence (QuiescenceEvent posted from
    slot_aboutToBlock).

What is missing is a way to feed commands to a running editor one at a
time from outside, and to get results back rather than only pass/fail.


Constraints from how the agent works
====================================

Claude Code runs each shell command as a separate process that must
finish before it sees the output.  It can start a long-running
background process, but it cannot write to that process's stdin in
later commands.  Therefore:

  * The editor must accept commands over some IPC channel that a
    separate, short-lived client process can connect to.
  * Each client invocation should send one command (or a short batch),
    wait for the reply, print it, and exit.
  * Replies should be deterministic: they should describe the state
    after the application has settled, so the agent needs no sleeps or
    retries.

The agent can read PNG files and view them as images, so screenshots
are a useful output, not only text.


Design
======

Overview
--------

  $ ./editor.exe -controlServer=out/ctl.gdvn &      # once, in background
  $ ./editor-ctl.py out/ctl.gdvn 'KeyPress("window1.editorFrame.m_editorWidget" "Key_X" "x")'
  Ok(null)
  $ ./editor-ctl.py out/ctl.gdvn 'QueryLabel("window1.m_statusArea.m_filename")'
  Ok("untitled.txt *")
  $ ./editor-ctl.py out/ctl.gdvn 'Screenshot("window1" "out/shot.png")'
  Ok(null)

The argument to -controlServer names an "access file" that the editor
writes when the server starts.  It holds what a client needs to connect
and authenticate (see "Transport and authentication").

Server side (editor)
--------------------

New command line option, "-controlServer=FILE".  When present, the
editor starts normally (it may also be given files to open) and
additionally creates a ControlServer object, which writes the access
file FILE.

ControlServer (new module control-server.{h,cc}, a QObject):

  * Listens on a QTcpServer bound to 127.0.0.1 with port 0, so the OS
    picks a free port, and writes the access file (see "Transport and
    authentication").  QTcpServer is in QtNetwork, which the editor
    does not link today; the local Qt build includes it
    (libQt5Network.a, Qt5Network.dll).
  * Protocol: the client sends one GDVN value, preceded by its length
    in bytes as a decimal number and a newline.  The value is a map:
      {key:"<access key>" cmd:<command or sequence of commands>}
    The server replies with one GDVN value in the same framing and
    closes the connection.  One connection per request keeps both
    sides simple.
  * Reply format, a tagged tuple:
      Ok(<result>)            result is `null` for actions
      Error("<message>")      the exception text from the command
  * A request whose key is missing or wrong gets Error("access denied")
    and no command is executed.  Requests that are malformed (bad
    length, oversized, not GDVN) are rejected the same way, and the
    connection is closed.  The server never executes anything before
    the key has been checked.
  * Commands are executed one at a time.  If a request arrives while a
    previous one is still waiting for quiescence, it waits its turn.
  * The server runs until the app exits, or until a Quit() command.
  * On startup, the server prints one line to stdout, such as
      control server listening on 127.0.0.1:PORT, pid N
    so the agent learns the process ID even if no command ever
    succeeds.

Transport and authentication
----------------------------

TCP on the loopback interface is used rather than local sockets
(QLocalServer).  On Windows, QLocalServer uses named pipes, which:

  * can be reachable from other machines over SMB (\\host\pipe\NAME)
    unless the server rejects remote clients, which depends on flags
    and Windows security settings that are hard to audit;
  * rely on Windows ACLs for access control, which are hard to reason
    about; and
  * would mean Windows and Linux use different IPC mechanisms (named
    pipes vs. Unix domain sockets).

With TCP, both platforms use the same mechanism, and access control is
the application's own key check, which is easy to understand and test.

Binding to 127.0.0.1 keeps other machines out.  It does not keep out
other local processes, including those of other users on a shared
machine, so every request must carry the access key.

The access file, written by the server at startup:

  {
    port: 54321
    key: "3f9c...e1"            // 32 random bytes, hex-encoded
    pid: 12345
  }

  * The key comes from a cryptographically secure generator,
    QRandomGenerator::system() (Qt 5.10+), and is new on every run.
  * The file is written to a temporary name in the same directory,
    then renamed, so a client never reads a partial file.
  * On Linux the file is created with mode 0600.  On Windows it gets
    the default ACLs of its directory, which normally means it is
    readable only by the user (and administrators).  So the key is
    protected by ordinary file permissions, the same trust boundary as
    the user's other files.
  * The server deletes the file on a clean exit.  If the editor is
    killed, the file remains, but the connection is refused, so a
    stale file fails safely.  The server overwrites an existing file
    at startup.
  * Including `pid` gives the agent the process ID for cleanup (see
    "Process lifecycle and cleanup") without a separate step.

The server compares keys in constant time.  That is cheap to do, even
though timing attacks over loopback are unlikely to matter.

Remote use: the design makes it easy to drive the editor from another
machine later, but the key and all traffic are sent unencrypted.
Rather than binding a non-loopback address, the recommended approach
is an SSH tunnel (`ssh -L PORT:127.0.0.1:PORT host`) with the access
file copied over, which keeps the server loopback-only and gets
encryption from SSH.  Binding other addresses directly would need TLS
(QSslSocket) first.

Browsers: a web page can make a browser connect to a port on
localhost.  The required key, plus a framing that is not HTTP, prevent
such a request from executing anything.  As a further guard, the server
can reject any request whose first bytes look like an HTTP request
line.

Executing a command:

  1. Parse the GDVN.  A syntax error produces Error(...).
  2. Run it through the same dispatcher used by event replay (see
     "Refactoring EventReplay" below), catching any exception and
     turning it into Error(...).  An error does not end the session.
  3. Wait for quiescence using the existing QuiescenceEvent /
     aboutToBlock mechanism, then send the reply.  For an action, the
     reply therefore means "the action was delivered and the app has
     settled".  For a query, the value is computed after the preceding
     action settled, which is automatic since commands are serialized.

Modal dialogs: QDialog::exec() runs a nested event loop.  Socket
notifications, posted events, and aboutToBlock all still work inside
it, so a command that opens a modal dialog gets its reply once the
dialog is up and idle, and later commands can drive the dialog.  This
needs to be verified early (step 2 below), since it is the main
reason for the shell.

Client side
-----------

editor-ctl.py, a small Python 3 script (Python is already a build
dependency):

  editor-ctl.py ACCESS-FILE COMMAND     (or "-" to read COMMAND from stdin)

It reads the port and key from ACCESS-FILE, connects to
127.0.0.1:PORT, sends the framed {key cmd} map, prints the reply, and
exits with status 0 for Ok, 1 for Error, and 2 for a connection
failure or a missing or unreadable access file.

There is currently no GDVN parser in Python.  The client needs to read
the access file, and only needs to tell Ok from Error in the reply (it
prints the reply text as-is).  So a small parser for the subset used
in the access file (a map whose values are integers and strings) is
enough, and the reply's tag can be found by looking at its first
token.  Alternatively, the access file could also be written in JSON
next to the GDVN version, but a second format adds little.

The fallback, if a Python client becomes cumbersome, is a small C++
client, editor-ctl.exe, using smbase's GDValue parser and either
QtNetwork (QTcpSocket) or plain sockets.

Refactoring EventReplay
-----------------------

Today EventReplay owns both the command dispatcher and the test driver
(the command sequence, the event loop, pass/fail).  Split it:

  * EventReplayExecutor (or keep the name EventReplay for the executor
    and add a new class for the driver): replayCall and the helpers it
    uses, the queued FocusKeySequence characters, and the quiescence
    detection.  It executes one command and signals when the app is
    quiescent afterward.
  * The .ev test driver: iterates over m_testCommands, calls the
    executor, and stops at the first failure, as now.
  * ControlServer: another client of the executor.

FocusKeySequence queues characters that are replayed one per
quiescence cycle.  The executor must report completion only after the
queue drains, for both clients.

The existing .ev tests are the regression suite for this refactoring:
`make check` must pass before anything else is added.

Queries
-------

The Check* commands compare against an expected value and throw on a
mismatch.  Interactively, the agent mostly wants the value.  For each
check that compares one value, add a Query* that returns it as a
GDValue, and re-implement the check as query-plus-compare:

  CheckLabel(path expect)          -> QueryLabel(path)
  CheckLineEditText(path expect)   -> QueryLineEditText(path)
  CheckFocusWidget(expect)         -> QueryFocusWidget()
  CheckQuery(path state expect)    -> Query(path state)
  CheckTableWidgetContents(...)    -> QueryTableWidgetContents(path)
  ... and so on.

This can be done gradually; the checks still work in the shell (they
return Ok(null) or Error), so only the most useful queries are needed
at first.

New commands
------------

  * DumpTree{path:"some.path" [options]}: return the QObject subtree rooted at
    `path` as GDVN.  For each object: objectName, class name, and the
    path to use in other commands.  For widgets also: visible, enabled,
    hasFocus, geometry, and, where meaningful, text (QLabel,
    QAbstractButton, QLineEdit), current item (combo boxes, lists), and
    window title.  Options limit the depth and omit invisible or
    unnamed objects.  An empty path means all top-level widgets.  This
    replaces guessing paths from the source code.  The existing
    DumpObjectTree prints Qt's text dump to stderr, which the client
    would not see.

    Note that this is a GDVN tagged map, not a tagged tuple, so the
    arguments are key/value pairs, like Python keyword arguments.  (That
    makes this interface easier to evolve without breaking
    compatibility.)

  * Screenshot(path filename): QWidget::grab() on the widget, saved as
    a PNG.  This lets the agent see layout and rendering problems that
    a tree dump cannot show.  It is similar to what CheckImage and
    eventReplayImage already do.

  * Quit(): close the application cleanly, running the normal
    shutdown checks (object counts and so on).

  * Ping(): return the editor's process ID (QCoreApplication::
    applicationPid()) and the listening port.  This confirms the server is
    responsive and tells the agent which process to kill if needed (see
    "Process lifecycle and cleanup").

Optional:

  * Session logging: -controlServerLog=FILE appends each successful
    action, and each query as the corresponding Check* with the
    observed value, in .ev syntax.  A useful session can then be edited
    into a regression test.  Given that most features should be tested
    with unit tests instead, this is a convenience, not a goal.


Running without visible windows
===============================

Driving the real "windows" platform plugin pops windows up on the
user's desktop, can steal focus while they work, and runs into the
focus races that the retry.sh wrappers work around.

The local Qt build includes qoffscreen.dll, so
QT_QPA_PLATFORM=offscreen may allow running with no visible windows,
while QWidget::grab() still renders.  This has not been tried with the
editor.  Focus and window activation may behave differently on the
offscreen platform (for example, QApplication::focusWidget and
ActivateWindow), so some commands may need adjusting there.  Try it
early (step 2), because if it works it removes both the intrusiveness
and most of the flakiness, and makes it reasonable for an agent to use
the shell without supervision.

If offscreen proves unworkable, the shell is still useful on the normal
platform, but the agent should use it only when asked.


Process lifecycle and cleanup
=============================

The agent starts the editor as a background task, and the editor must
not be left running if Quit() fails (the server hangs, the app
deadlocks, or a modal dialog blocks shutdown).

On 2026-11-22 the agent tested, in this environment, what it can do,
using a stand-in native Windows program (PING.EXE -n 120) launched as
a background task from the Cygwin bash tool:

  * Detecting that it is still running:
    - The Claude Code harness notifies the agent when a background
      task exits.
    - Cygwin `ps -W` lists native Windows processes with their Windows
      PIDs, and showed the stand-in process.

  * Killing it, both of which worked:
    - The harness's task-stop tool, given the background task ID,
      killed the native process along with its shell.
    - `taskkill /F /PID <winpid>` killed it by Windows PID without
      using the harness.  This is the fallback when the task ID is not
      available, such as after a context reset, or when the editor was
      started some other way.

That test used a console program, not a GUI one.  Step 2 should repeat
it with editor.exe.

Rules for the agent, which should go into CLAUDE.md along with the
other guidance in step 5:

  * Kill by PID, never by image name.  The user may have their own
    editor.exe instances running, and `taskkill /IM editor.exe` would
    kill those too.  The PID comes from the access file, the startup
    line, or Ping().

  * Kill the whole process tree.  The editor starts child processes
    (editor-fs-server.exe, clangd, lsp-test-server.py), which may
    survive if only the editor is killed.  Use
    `taskkill /F /T /PID <winpid>`, then confirm with `ps -W` that
    nothing remains.

  * Prefer Quit(), because a forced kill skips the normal shutdown
    checks (object counts and so on).  If Quit() hangs, kill the
    process, and report the hang, since it is a bug in its own right.


Steps
=====

Each step is a commit that builds and passes `make check`.

  1. Refactor EventReplay into an executor and the .ev driver, with no
     behavior change.

  2. Add ControlServer, -controlServer, and editor-ctl.py, running
     commands through the executor with Ok/Error replies after
     quiescence, plus the access file, key checking, Ping(), Quit(),
     and the startup PID line.  Verify by hand: open a modal dialog, then drive it; try
     QT_QPA_PLATFORM=offscreen; and confirm that the agent can detect
     and kill a running editor.exe, including its child processes, as
     described in "Process lifecycle and cleanup".

  3. Add DumpTree and Screenshot.

  4. Add Query* commands, starting with QueryLabel, QueryLineEditText,
     QueryFocusWidget, QueryFocusWindowTitle, and Query, re-expressing
     the corresponding Check* in terms of them.

  5. Update doc/event-replay.txt to describe the shell and the new
     commands, and add a paragraph to CLAUDE.md saying when the agent
     may use the shell (for example, "only with
     QT_QPA_PLATFORM=offscreen" or "only when asked").  CLAUDE.md
     currently says the agent should not run GUI tests unless directed.
     Also add the cleanup rules from "Process lifecycle and cleanup".

  6. (Optional) Session logging.

Testing:

  * The protocol framing, request validation (including rejecting a
    missing or wrong key, oversized lengths, and HTTP-looking input),
    reply formatting, and access-file writing and reading can be unit
    tested without a GUI if they are factored as pure functions
    (GDValue in, bytes out and back).
  * An automated end-to-end test would start the editor with
    -controlServer, run a few editor-ctl.py commands, and Quit().  It
    pops up a window unless offscreen works, so it belongs with the GUI
    tests in `make check`, not in the `make` default target.


Alternatives considered
=======================

  * Desktop "computer use" (screenshots plus synthetic mouse and
    keyboard at the OS level): available only in the Claude desktop
    app, not the CLI; slower; and less precise than addressing widgets
    by object path.  It also cannot read object names or widget state.

  * Local sockets (QLocalServer): named pipes on Windows, Unix domain
    sockets on Linux.  Rejected for the reasons in "Transport and
    authentication".

  * Reading commands from a file that the editor polls: simpler to
    build than a socket, but replies need a second file, and
    synchronization by polling is clumsy.  A reasonable fallback if
    QtNetwork is unwanted.

  * Existing tools: GammaRay (inspection, GUI-oriented), Squish
    (commercial automation), QtTest (in-process, compiled tests).  None
    is designed to be driven by one-shot shell commands, and none
    reuses the existing .ev vocabulary.


Open questions
==============

  * QtNetwork dependency.  QTcpServer lives in QtNetwork, which the
    editor does not currently link (it uses Widgets, Gui, Core).
    Options: link QtNetwork (only the control server uses it); use
    plain BSD/Winsock sockets with a QSocketNotifier; or use the
    file-polling alternative.  Linking QtNetwork is the simplest.

  * Key handling.  Anyone who can read the access file can control the
    editor, which is the intended trust boundary (the user's own file
    permissions).  If the access file is put somewhere shared, such as
    a world-readable directory on Linux, that boundary is lost; the
    0600 mode guards against that on Linux, and on Windows the
    directory's ACLs are relied on.

  * Which binary.  Building the server into editor.exe means the shell
    works with the real application.  The alternative is a separate
    test build, which seems unnecessary given that it is off by
    default.

  * Whether to keep a single name, EventReplay, for the executor, and
    name the .ev driver something like EventReplayTest.
