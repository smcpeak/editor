ui-shell.txt
Explanation of mechanism and usage of UI shell subsystem


Usage
=====

The UI shell executes commands, and checks application state, based on
instructions in a "UI Shell Language" (UIS) file.  The conventional
extension is ".uis".

A UIS file can be executed in the editor by passing the
"-uisCmds=file.uis" command line argument.  There is also the
"-testCommands=cmds.gdvn" argument that can execute many UIS files
within a single process for improved efficiency.  These options are
not specific to the editor; see "Using the UI shell in another
program", below.

The syntax of a UIS file uses GDVN (see smbase/gdvalue-design.txt).  It
has an outer map with keys `args`, `includes` and `cmds`.  `args`
specifies the command line arguments for that test (in the editor,
usually the name of a file to open).  `includes` names files whose
`Define`s are used in `cmds`, such as test/common-defns.gdvn.  `cmds`
is a sequence of tagged containers where the tag is the command name
and the container elements provide its arguments.

The "-record" command line switch can create a sequence of input event
commands (keystrokes, etc.) to start with.  Checks are then inserted
manually.

Example (from test/read-only1.uis):

  // Verify we can make a change and undo it.
  KeyPress("window1.frame1.editorFrame.m_editorWidget" "Key_X" "x")
  CheckLabel("window1.m_statusArea.m_filename" "untitled.txt *")
  Shortcut("window1.m_menuBar.editMenu.editUndo" "Alt+Backspace")
  CheckLabel("window1.m_statusArea.m_filename" "untitled.txt")

UI input commands are simulated by posting them to the Qt event queue,
usually with the receiver object indicated by a QObject name path.

Checks usually work by identifying an object (by path) and querying it
somehow to yield a GDV value (usually a string) that is then compared to
what is in the test script.


Classes
=======

Dependencies (arrows point at what is used):

  UIShellScriptRunner ---> UIShellExecutor
                                 |
                                 v
                       UIShellCommandHandler --> UIShellQueryable
                                 ^                     ^
                                 | (inherits)          | (inherits)
                       UIShellGUICommandHandler --> UIShellGUIQueryable

UIShellScriptRunner handles reading the test/*.uis scripts and executing
all of its commands in sequence.  It is given a UIShellCommandHandler
(in the editor, a UIShellGUICommandHandler owned by the caller), and
owns a UIShellExecutor that uses it.  It runs its own top-level Qt
event loop, taking the place of the usual application top-level loop.

UIShellExecutor is responsible for executing commands one at a time and
waiting for the app to become quiescent between them (see below).  It
only depends on QtCore, and does not know what any command means; it
passes each one to a UIShellCommandHandler.

UIShellCommandHandler interprets the commands that do not need widgets:
Sleep, CheckQuery and the other query checks, and the file commands.
It passes any other command to a virtual method for a derived class to
handle.  A command can also leave "pending steps", which the executor
performs one per quiescence point after the command itself.  For
example, FocusKeySequence types one character per step.

UIShellGUICommandHandler derives from UIShellCommandHandler and adds
the commands that synthesize input for, or inspect, widgets, finding
them by QObject name path.

UIShellQueryable is an interface that widgets can implement to allow the
UI shell to perform widget-specific queries.  This way, scripts can
directly interrogate (possibly invisible) application state rather than,
say, primarily relying on screenshots.  However, UIShellGUIQueryable
extends it with a way for widgets to yield images (screenshots) when
necessary.

UIShellResult holds the result of a single command (success or error)
for passing between UI shell components.

UIShellScriptFile (ui-shell-script-file) reads a .uis file: it
processes `includes`, substitutes the `Define`s, and flattens `cmds`
into a list of commands.

ui-shell-app has what a GUI program needs to be driven by the UI
shell: UIShellOptions recognizes "-uisCmds" and "-record",
`runUIShellScript` runs a script with a UIShellScriptRunner, and
`runUIShellTestCommandsIfRequested` implements "-testCommands".

Because the executor, the base handler and the script file reader do
not need widgets, they have unit tests (ui-shell-executor-test.cc,
ui-shell-command-handler-test.cc and ui-shell-script-file-test.cc).
The GUI commands are tested by ui-shell-gui-test (below).


Using the UI shell in another program
=====================================

None of the classes above depend on the editor.  To make another Qt
GUI program scriptable, as the editor and ui-shell-gui-test do:

  * In `main`, call `runUIShellTestCommandsIfRequested`, passing the
    function that does the real work (`innerMain`), which must create
    its own QApplication.

  * In `innerMain`, pass each argument to
    `UIShellOptions::processOption`, and include
    `UIShellOptions::helpText()` in the usage message.

  * Give the top-level windows and the widgets that scripts refer to
    object names, since that is how paths find them.

  * Create an EventRecorder if "-record" was given.

  * If a script was given, call `runUIShellScript` with a
    UIShellGUICommandHandler (or a class derived from it that adds
    program-specific commands) and a global self-check function.

ui-shell-gui-test.cc is a small, complete example.


ui-shell-gui-test
=================

ui-shell-gui-test.exe is a stand-alone program whose only purpose is
to be driven by UI shell scripts.  It has an example of each kind of
widget that the GUI commands operate on: a main window with a menu
bar, three modal dialogs (Edit Name, Table, and a QMessageBox) and a
modeless List Window.

Its original design is in doc/plans/claude-ui-shell-gui-test.txt, but
(per the intent of the `plans` directory) it isn't updated as further
changes are made.  Important design aspects are described here instead.

Its scripts are in test/uisgt/, roughly one per command, and
test/uisgt/all-uisgt-tests.gdvn lists them.  `make check` runs them
with:

  ./ui-shell-gui-test.exe -testCommands=test/uisgt/all-uisgt-tests.gdvn

before the editor's .uis tests, since those depend on the commands
working.  An individual script can be run with:

  ./ui-shell-gui-test.exe -uisCmds=test/uisgt/<name>.uis

The program adds one command of its own, `CheckFails(<check>
"<regex>")`, which runs a Check* or WaitUntilCheck* command and
succeeds only if it fails with a message matching the regex.  Since
most bugs in a check would make it pass when it should not, each
check-* script uses CheckFails to confirm that a wrong expected value
is reported, and with a useful message.

When adding a command to UIShellGUICommandHandler:

  * If the command needs a kind of widget that ui-shell-gui-test does
    not have yet, add one to the appropriate window, with an object
    name, and if it has interesting state, something (usually a
    label) that shows it.

  * Add test/uisgt/<command>.uis.  As the others do, start with a
    CheckFocusWidget or CheckFocusWindow, so a problem with the
    initial focus is reported as such.  For a check, use CheckFails
    with at least one wrong expected value.

  * Add the script to test/uisgt/all-uisgt-tests.gdvn.

Commands that do not need widgets belong in UIShellCommandHandler and
should be tested in ui-shell-command-handler-test.cc instead.


Quiescence detection mechanism
==============================

The main technical challenge is to properly synchronize commands and
checks with the application.  We can't just post all the events at the
start, among other reasons because the receivers won't exist yet.  A
simple approach is to post them using a fixed timer, but that leads to
tension between reliability (long timer) and test speed (short timer).
The UI shell system can be instructed to use a timer via the
UI_SHELL_DELAY_MS environment variable, but that is mainly for
debugging.

Instead, the basic idea of the normal mechanism is to post an event or
do a check, then wait for the application to reach quiescence, then post
the next, etc.

But how do we detect quiescence?


Failed attempt 1: Single event loop
-----------------------------------

My first approach was to replace the top-level event loop ("exec()"
call) with something like:

  while (events) {
    dequeue and post input event;
    QCoreApplication::processEvents();   // drain event queue
  }

This does not work because if event processing starts a modal dialog,
control never returns to the loop since the modal dialog starts its own
event loop.


Failed attempt 2: Low-priority event
------------------------------------

The next approach was to post a low-priority "quiescence" event.  Then
the event handler was basically:

  dequeue and post input event;
  post QuiescenceEvent;

This fails for a more subtle reason.  Anywhere in the guts of Qt,
something could drain the event queue on its own by calling
processEvents(), which would trigger the QuiescenceEvent, even though
the app wasn't actually quiescent because whatever was meant to happen
after processEvents() was still pending.  This turns out to happen when
QMessageBox closes.  The effect is I would execute the next command
before the dialog has exited, which fails of course.


Failed attempt 3: Timer with zero interval
------------------------------------------

The documentation QObject::startTimer says, "If interval is 0, then the
timer event occurs once every time there are no more window system
events to process."  The meaning of this statement is unclear (what
exactly is a "window system event" in this context?), but empirically,
getting a timer notification with a zero interval does *not* imply the
application is quiescent, so that's out too.


What works: aboutToBlock
------------------------

The current approach is to hook into the
QAbstractEventDispatcher::aboutToBlock signal.  For illustration of its
behavior, here is the Windows implementation of emitting that signal, in
qeventdispatcher_win.cpp:

  canWait = (!retVal
             && !d->interrupt
             && (flags & QEventLoop::WaitForMoreEvents));
  if (canWait) {
    ...
    emit aboutToBlock();
    waitRet = MsgWaitForMultipleObjectsEx(..., INFINITE, ...);
    emit awake();

We can see that `aboutToBlock` is only called if the innermost event
loop hasn't exited (`!d->interrupt`) and we are processing events with
the intent to block if there are none (`QEventLoop::WaitForMoreEvents`).
The latter eliminates the problem with a random processEvents() call
somewhere in the Qt guts, since that won't block.

This suggests doing event posting and checking in `aboutToBlock`, but
that has a subtle problem: if nothing adds anything to the OS event
queue, then `emit aboutToBlock()` will return and drop straight into
WaitFor, which will block, hanging the test until an OS event happens to
arrive.  Furthermore, it seems like a bad idea to do a lot of work,
especially sending events synchronously (like what "TriggerAction"
does), inside the `aboutToBlock` signal handler, since it is called from
a weird spot in the guts in the Qt event handler.

Therefore, `slot_aboutToBlock` merely posts QuiescenceEvent and calls
QAbstractEventDispatcher::instance()->wakeUp().  The latter posts an OS
event so that WaitFor will return immediately.  Then the QuiescenceEvent
will be dispatched in the normal way from whatever is the innermost
event loop, and that is where we do command execution and checking.
When that is finished and the app returns to quiescence, `aboutToBlock`
will again be invoked, repeating the cycle.

When the test is done, we simply disconnect `aboutToBlock`.

Portability note: On Windows, the `aboutToBlock` and `awake` signals are
emitted as shown in the code snippet above.  But on Linux, the `awake`
is not emitted right after calling `poll`, but instead only just before
events are dequeued and dispatched (Windows also emits `awake` there; it
does so in two places).  This means that a lot can happen in the app
before `awake` fires, including terminating and starting new event
loops.  This is why the `os-wait-timer` module only works on Windows; in
this respect, the Linux implementation of Qt is deficient.


IPC and g_waitingCounter
------------------------

The above isn't quite sufficient to detect quiescence when an operation
has to wait for interprocess communication and pumps the event queue
while waiting (e.g., RFA_AsyncMultiClient).  In that case, the event
queue entirely drains and we block, but UI shell command execution
should not continue because we intend to wait for the other process to
respond.

The solution to the IPC problem is the global `g_waitingCounter`
declared in `waiting-counter.h`, and usually manipulated with the
`IncDecWaitingCounter` class.  When that counter is non-zero, quiescence
events are ignored rather than triggering the next command execution.

Code that awaits IPC must manually arrange to increment
`g_waitingCounter`.  Fortunately, when that is not done, the result is
usually a deterministic test failure due to the UI shell executing the
next command before the IPC has a chance to respond, rather than a race.
